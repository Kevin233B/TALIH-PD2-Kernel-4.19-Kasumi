# Linux 4.19 compat

This branch carries the compat changes needed to build `kasumi_lkm.ko`
against an arm64 **Linux 4.19** kernel (developed on a MediaTek MT8797
Android kernel, clang r383902, out-of-tree `make M=... modules`).

Base: upstream `4c320eb5e044` ("feat: bind isolated mount views to detected
owners").

## Changes so far

### src/core/kasumi_runtime.{h,c}
- `task_work_add()` takes `bool notify` before kernel 5.10 (the
  `enum task_work_notify_mode` argument arrived in 5.10); the
  `kasumi_task_work_add_ptr` declaration and definition are version-guarded
  with the 4.19 `bool` variant.

### src/hooks/kasumi_proc_hooks.c
- `TWA_RESUME` only exists from 5.10; shimmed to `true` for older kernels.
- `access_ok()` takes a `type` argument before 5.0; the 2-argument form is
  gated to `< 5.0` with `VERIFY_WRITE` (arm64 ignores the type argument).

### src/core/kasumi_dirhijack.c
- `super_operations.free_inode` only exists from 5.9 (split out of
  `destroy_inode`). For older kernels the inode-free handoff falls back to
  `orig->destroy_inode`.

### src/core/kasumi_sop_shadow.c
- same `free_inode` handling for the shadow `super_operations` gate and
  install path; `#include <linux/version.h>` added.

### src/features/kasumi_fake_mountinfo.c
- `seq_read_iter()` only exists from 5.10 and 4.19 seq files serve
  `->read = seq_read`, so the mountinfo snapshot reader falls back to
  `kernel_read()` for `LINUX_VERSION_CODE < 5.10`;
  `#include <linux/version.h>` added.

### src/core/kasumi_hide_events.c
- `fsnotify_ops.handle_inode_event` only exists from 5.1; on older kernels
  the group is wired through a `handle_event` adapter (`hide_handle_event`)
  matching the 4.19 callback shape and forwarding to
  `hide_directory_event()`, building a temporary `struct qstr` from the raw
  `(const unsigned char *)file_name` (NUL-terminated on 4.19).
- `fsnotify_add_mark()` takes 5 arguments from 5.9 (and a different 4 from
  6.12); for `LINUX_VERSION_CODE < 5.9` the 4-argument
  `fsnotify_add_mark(mark, connp, type, allow_dups)` form is used with
  `allow_dups = 1` (multiple per-directory name watches share one group).

### src/core/kasumi_hide_rules.c
- `cancel_work()` only exists from 6.0 (non-blocking cancel); before that
  `cancel_work_sync()` is used instead — the sibling
  `kasumi_hide_rules_stop()` uses the same idiom, and `quiesce()` draining
  an executing resolver is the intended behavior anyway;
  `#include <linux/version.h>` added.

### src/policy/kasumi_path_policy.c
- 4.19 predates the xarray API (added in 4.20; the 4.19 tree only ships a
  24-line `xarray.h` stub). The policy uid sets are plain uid -> marker
  maps, so they are backed by the idr API through same-named local helpers
  (`xa_init/xa_destroy/xa_load/xa_store/xa_err`), using `idr_alloc_u32()`
  for exact-uid allocation across the full u32 range. The struct fields and
  the `kasumi_policy_build_uid_list()` parameter switch to `struct idr` for
  `< 4.20`.
- the openat2-style `LOOKUP_*` flags (`LOOKUP_NO_SYMLINKS`,
  `LOOKUP_NO_MAGICLINKS`, `LOOKUP_BENEATH`, `LOOKUP_IN_ROOT`,
  `LOOKUP_CACHED`) only exist from 5.6. They are carried in kasumi's own
  resolver flag space and do not collide with any 4.19 `LOOKUP_*` bit
  (4.19's highest is `LOOKUP_DOWN` 0x8000), so the mainline values are
  defined for `< 5.6`.

### src/features/kasumi_owner.c
- same `fsnotify_ops.handle_inode_event` adapter treatment as
  `kasumi_hide_events.c` (`kasumi_owner_handle_event` forwarding to
  `kasumi_owner_event()` with a temporary `struct qstr`), and the same
  4-argument `fsnotify_add_mark()` form for `< 5.9`.

### src/hooks/kasumi_ftrace_hooks.c
- `#include "kasumi_vfs_hooks.h"` added: the `kasumi_krp_*` /
  `kasumi_kp_*` handlers referenced here are declared only in that header;
  upstream relied on implicit declarations (tolerated by GCC, an error
  under clang 16+ and under `-Werror-implicit-function-declaration`
  kernels). This is a real fix for every kernel, not just 4.19.

## Status

`kasumi_lkm.ko` builds end-to-end against 4.19 (compile + link): the module
carries 182 undefined imports, all resolving against the target kernel's
`Module.symvers` (including the real `register_kprobe` /
`register_kretprobe` machinery), and the vermagic matches the producing
kernel (`4.19.191+ SMP preempt mod_unload modversions aarch64`). Runtime
behavior on the target device still needs validation; further fixes are
expected only if device testing surfaces issues.

Kernel-side requirements (outside this module's control — they live on the
target kernel tree, not here):

- `CONFIG_KPROBES=y` — the runtime resolver registers a kprobe on
  `kallsyms_lookup_name` to learn its address; with `CONFIG_KPROBES=n`
  `register_kprobe()` compiles to an inline `-ENOSYS` stub and every
  resolved symbol would silently be `NULL`.
- `CONFIG_FUNCTION_TRACER=y` — so `ftrace.o` and `register_ftrace_function`
  exist for the ftrace-based hooks.
- the `.ko` must be paired with the kernel build it was produced against
  (vermagic and symbol CRCs must match).
